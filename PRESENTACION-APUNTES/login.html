Autenticación

Flujo de Login y Sesión

Cómo Spring Security autentica usuarios, protege la sesión y enruta al portal correcto según el rol.

Endpoints del formulario

Método URL Descripción
GET /login Muestra el formulario de login
POST /login Spring Security procesa las credenciales (campo username + password)
GET /change-password Forzar cambio de contraseña (flag must_change_password)
POST /logout Invalida sesión → redirige a /login?logout

Parámetros de alerta en /login

Parámetro Causa Mensaje
?error Credenciales incorrectas "Correo o contraseña incorrectos"
?logout Cierre de sesión correcto "Sesión cerrada correctamente"
?expired Segunda sesión simultánea Sesión caducada por límite concurrent
?norole Usuario sin ningún rol asignado "Tu cuenta no tiene ningún rol asignado"

Lógica de redirección post-login (CustomLoginSuccessHandler)

La clase CustomLoginSuccessHandler implementa AuthenticationSuccessHandler y decide adónde redirigir al usuario tras autenticarse correctamente:

1. ¿must_change_password? → Sí → /change-password
2. Contar roles funcionales (ADMIN, ADMIN_CENTRO, PROFESOR, ALUMNO) → >1 rol → /seleccionar-rol
3. Exactamente 1 rol → ADMIN → /admin/dashboard
ADMIN_CENTRO → /centro-admin/dashboard
PROFESOR → /profe/dashboard
ALUMNO → /alumno/dashboard
4. 0 roles funcionales → /login?norole

Protecciones de sesión

Session Fixation

changeSessionId() — al autenticarse, Spring asigna un nuevo ID de sesión. Esto evita que un atacante fije el ID antes del login.

Sesiones concurrentes

maximumSessions(1) — solo 1 sesión activa por usuario. Un segundo login desde otro dispositivo expira la sesión anterior → /login?expired.

Timeout de sesión

30 minutos de inactividad (server.servlet.session.timeout=30m). Configurado en application.properties.

Cookie segura

HttpOnly=true, SameSite=strict en todos los entornos. En producción, además Secure=true (HTTPS obligatorio).

Rate limiting en login (Bucket4j)

La clase LoginRateLimitFilter se inserta en el filtro de Spring Security antes de UsernamePasswordAuthenticationFilter.

Parámetros: 10 intentos por IP cada 15 minutos. El intento número 11 recibe HTTP 429 Too Many Requests. Basado en el algoritmo Token Bucket (librería Bucket4j). 
// Posición en la cadena de filtros (SecurityConfig)
http.addFilterBefore(loginRateLimitFilter,
    UsernamePasswordAuthenticationFilter.class);

Contraseñas

BCryptPasswordEncoder: Spring Security usa BCrypt para hashear contraseñas. No se almacenan en texto plano. La verificación se hace comparando el hash del input con el password_hash almacenado en la tabla usuarios.

El campo must_change_password (booleano en usuarios) se puede activar por un administrador. Al hacer login, CustomLoginSuccessHandler lo comprueba antes de cualquier otra lógica.

Spring Session JDBC

Las sesiones se almacenan en la base de datos (no en memoria del servidor) en las tablas SPRING_SESSION y SPRING_SESSION_ATTRIBUTES. Esto permite escalar horizontalmente sin perder sesiones.

Estas tablas se crean en V1__schema_definitivo.sql junto al resto del esquema.

Preguntas frecuentes

¿Qué hace CustomLoginSuccessHandler si el usuario tiene 2 roles?

Redirige a /seleccionar-rol pasando los roles como atributo de la sesión para que la página muestre las tarjetas correspondientes.

¿Qué es la Session Fixation y cómo se previene?

Es un ataque donde el atacante conoce el ID de sesión antes del login (p.ej. por URL). Spring previene esto con changeSessionId(): al autenticarse correctamente, el ID de sesión cambia, invalidando cualquier ID previo.

¿Qué pasa si un usuario abre sesión en dos dispositivos a la vez?

Con maximumSessions(1), la primera sesión se marca como expirada. Al intentar hacer cualquier petición con ella, Spring redirige a /login?expired.

¿Qué clase gestiona las contraseñas?

BCryptPasswordEncoder registrado como bean en Spring. En el login, Spring Security invoca automáticamente matches(rawPassword, encodedPassword) para verificar sin desencriptar.
