Arquitectura y diseño
01
Arquitectura
¿Por qué elegiste Spring Boot y no otro framework como Django o Express?
voltear →
Respuesta
Spring Boot 3.3 sobre Java 21 ofrece Spring Security integrado con RBAC nativo, Spring Data JPA para el ORM y Spring Session JDBC para sesiones persistentes en PostgreSQL. El ecosistema unificado evita ensamblar librerías independientes para cada capa. Además, Java 21 con Virtual Threads mejora la concurrencia sin cambiar el modelo de programación.
02
Arquitectura
¿Por qué Thymeleaf en lugar de React o Angular?
voltear →
Respuesta
Thymeleaf es SSR (Server-Side Rendering): no existe API REST pública que proteger, se elimina la superficie de ataque de CORS y JWT, y el token CSRF lo gestiona Thymeleaf automáticamente con th:action. El tiempo de desarrollo en solitario también favorece evitar dos aplicaciones separadas.
03
Arquitectura
¿Qué es RBAC y cómo lo implementaste?
voltear →
Respuesta
Role-Based Access Control: los permisos se asignan a roles, no a usuarios directamente. Implementado con tabla intermedia usuarios_roles (N:M). Cada controlador lleva @PreAuthorize("hasRole('X')") a nivel de clase más los URL matchers de SecurityConfig. Doble capa de defensa.
04
Arquitectura
¿Qué es la entidad Impartición y por qué es el pivot central del modelo?
voltear →
Respuesta
Impartición vincula cuatro dimensiones: qué (Módulo), quién (Profesor), a quién (Grupo de alumnos) y dónde (Centro). Es el nodo del que cuelgan las Matrículas, los PeriodosEvaluacion y los ItemsEvaluables. Sin ella no existe calificación ni auditoría.
05
Arquitectura
¿Cómo garantizas el aislamiento multi-sede a nivel de base de datos?
voltear →
Respuesta
La columna centro_id aparece como clave foránea en grupos, imparticiones y matriculas. Toda consulta académica filtra por ese campo. Para el rol ADMIN_CENTRO, el componente CentroAdminContextService inyecta los centro_id permitidos como predicado obligatorio en cada operación antes de ejecutarla.
06
Arquitectura
¿Cómo funciona la relación N:M entre usuarios y roles?
voltear →
Respuesta
La tabla intermedia usuarios_roles relaciona usuario_id con rol_id. Los roles se cargan con FetchType.EAGER para que Spring Security los tenga disponibles en cada petición sin consultas adicionales al autenticar. Esto permite que un mismo usuario tenga varios roles simultáneos (p.ej. Profesor + Alumno).
07
Arquitectura
¿Qué es una Matrícula en tu sistema y qué estados puede tener?
voltear →
Respuesta
Una Matrícula vincula un alumno (Usuario) con una Imparticion concreta dentro de un Centro. Sus estados son: ACTIVA, BAJA y CONVALIDADO. También almacena el flag esRepetidor. No puede eliminarse si tiene calificaciones registradas.
08
Arquitectura
¿Qué diferencia hay entre el rol Admin Global y el Admin de Centro?
voltear →
Respuesta
El Admin Global (ROLE_ADMIN) tiene acceso irrestricto a toda la plataforma: todos los centros, el catálogo de módulos y la auditoría forense global. El Admin de Centro (ROLE_ADMIN_CENTRO) usa las mismas herramientas pero acotadas a sus centros asignados, y no puede cambiar roles de usuarios ni ver datos de otras sedes.
Seguridad y OWASP
09
Seguridad
¿Qué es OWASP Top 10 y cuántas categorías abordaste?
voltear →
Respuesta
OWASP Top 10 es el estándar de las diez vulnerabilidades web más críticas. En el proyecto se identificaron y remediaron 9 categorías: A01 (Broken Access Control), A02 (credenciales hardcoded), A03 (XSS via th:utext), A04 (rate limiting login), A05 (headers HTTP y gestión de sesiones), A06 (snap-admin vulnerable), A07 (política de contraseña), A09 (log de eventos de seguridad). Con 32 tests de seguridad automatizados.
10
Seguridad
¿Cómo protegiste la aplicación contra XSS?
voltear →
Respuesta
Uso exclusivo de th:text en todas las plantillas Thymeleaf para datos de usuario o BD (auto-escapado HTML implícito). Se auditaron exhaustivamente todos los templates: cero ocurrencias de th:utext con datos dinámicos. Adicionalmente, la cabecera Content-Security-Policy restringe los scripts a 'self'.
11
Seguridad
¿Cómo protegiste contra CSRF?
voltear →
Respuesta
Spring Security 6 habilita la protección CSRF por defecto. Thymeleaf incluye automáticamente el token CSRF en cada formulario que usa th:action="@{/ruta}". Un POST sin token válido devuelve HTTP 403. La cookie de sesión tiene SameSite=Strict como capa adicional.
12
Seguridad
¿Qué es el rate limiting y cómo lo implementaste?
voltear →
Respuesta
El filtro LoginRateLimitFilter (Bucket4j 8.10.1, algoritmo token bucket) limita a 10 intentos de POST /login por IP cada 15 minutos. El intento 11 recibe HTTP 429. La IP se resuelve desde X-Forwarded-For para funcionar detrás de proxy. Registrado en SecurityConfig antes de UsernamePasswordAuthenticationFilter.
13
Seguridad
¿Qué es session fixation y cómo la previste?
voltear →
Respuesta
Session fixation: un atacante obtiene un ID de sesión antes del login y lo reutiliza tras la autenticación. Prevención: sessionFixation().changeSessionId() en SecurityConfig regenera el ID de sesión justo después del login exitoso, invalidando cualquier sesión prefijada. Además, maximumSessions(1) impide sesiones concurrentes.
14
Seguridad
¿Qué es IDOR y cómo lo preveniste en el portal del alumno?
voltear →
Respuesta
IDOR (Insecure Direct Object Reference): manipular un ID en la URL para acceder a datos ajenos. En el portal del alumno, UsuarioService.getStudentGrades(usuarioId, periodoId) verifica que el periodoId pertenece a una impartición donde el alumno autenticado tiene matrícula activa. Si no es suyo, lanza AccessDeniedException.
15
Seguridad
¿Qué era snap-admin y por qué fue un problema de seguridad crítico?
voltear →
Respuesta
snap-admin:0.2.1 instalaba un panel CRUD automático sobre todas las entidades JPA en /snap-admin/**, sin pasar por el SecurityConfig de la app. Cualquier persona con acceso a la red podía listar, crear y eliminar cualquier registro. Se eliminó la dependencia del pom.xml y se añadió .requestMatchers("/snap-admin/**").denyAll() como salvaguarda permanente.
16
Seguridad
¿Qué hace @ValidPassword y dónde se aplica?
voltear →
Respuesta
Es una anotación Bean Validation personalizada con su PasswordConstraintValidator. Exige: mínimo 8 caracteres, al menos una mayúscula, una minúscula y un dígito. Se aplica al campo password de AdminUsuarioFormDTO y a los usuarios creados por importación Excel. En la edición, el campo es opcional: si está vacío, el hash existente se conserva sin regenerar.
17
Seguridad
¿Qué cabeceras HTTP de seguridad añadiste y para qué sirven?
voltear →
Respuesta
Content-Security-Policy: evita XSS restringiendo orígenes de scripts (default-src 'self', frame-ancestors 'none'). Referrer-Policy strict-origin-when-cross-origin: evita fuga de URLs internas. Permissions-Policy: deshabilita cámara, micrófono y geolocalización. Spring Security 6 añade por defecto X-Content-Type-Options, X-Frame-Options: DENY y HSTS.
18
Seguridad
¿Qué hace MustChangePasswordFilter y cuándo entra en acción?
voltear →
Respuesta
Es un OncePerRequestFilter registrado tras UsernamePasswordAuthenticationFilter. En cada petición autenticada lee el atributo de sesión mustChangePassword. Si es true, redirige a /change-password sin importar la ruta destino. Se salta rutas estáticas y de gestión de sesión. CustomLoginSuccessHandler es quien escribe ese atributo al hacer login.
Base de datos y persistencia
19
Base de datos
¿Por qué PostgreSQL en lugar de MySQL?
voltear →
Respuesta
PostgreSQL ofrece tres funcionalidades que MySQL no tiene de forma nativa y que el proyecto necesita: JSONB para el campo configuracion de centros, triggers PL/pgSQL para la auditoría forense inmutable, y la función current_setting() que permite transmitir el email del profesor desde la app al trigger de auditoría dentro de la sesión.
20
Base de datos
¿Cómo funciona el trigger de auditoría PL/pgSQL?
voltear →
Respuesta
El trigger trigger_auditoria_notas se dispara AFTER UPDATE sobre la tabla calificaciones. La función registrar_cambio_nota() inserta en auditoria_notas el valor anterior (OLD.valor), el nuevo (NEW.valor), la fecha exacta y el email del docente leído de la variable de sesión app.usuario_actual. Solo actúa cuando el valor cambia realmente (IS DISTINCT FROM).
21
Base de datos
¿Cómo transmites el email del profesor desde Java al trigger de PostgreSQL?
voltear →
Respuesta
Dentro de la transacción de TeacherDashboardService.upsertGrades(), antes de persistir las calificaciones, se ejecuta la native query: SELECT set_config('app.usuario_actual', :email, true). Esto escribe el email en la sesión de PostgreSQL para esa transacción. El trigger lo lee con current_setting('app.usuario_actual', true).
22
Base de datos
¿Qué es Flyway y por qué lo usas en lugar de Hibernate ddl-auto?
voltear →
Respuesta
Flyway aplica migraciones SQL versionadas (V1__, V2__…) de forma reproducible y auditable. Hibernate ddl-auto no puede gestionar triggers PL/pgSQL ni datos de seed complejos. Con Flyway el esquema es explícito, versionado en git, y se puede reproducir exactamente el mismo estado en cualquier entorno (dev, CI, producción).
23
Base de datos
¿Qué es Spring Session JDBC y por qué lo usas?
voltear →
Respuesta
Spring Session JDBC almacena las sesiones HTTP en tablas de PostgreSQL (SPRING_SESSION y SPRING_SESSION_ATTRIBUTES). Esto permite: (1) que las sesiones sobrevivan a reinicios de la app, (2) que maximumSessions(1) funcione sin caché externa (Redis, etc.), y (3) que la sesión expire a los 30 minutos configurados en server.servlet.session.timeout.
24
Base de datos
¿Cómo se calcula la nota final ponderada de un alumno?
voltear →
Respuesta
El cálculo tiene tres niveles: CE → RA ponderado por el campo peso de CriterioEvaluacion (fallback: media simple si todos los pesos son 0). RA → Periodo ponderado por ResultadoAprendizaje.pesoSugerido. Periodo → Global ponderado por PeriodoEvaluacion.peso. Todo se lee de la base de datos; no hay constantes hardcoded en el código.
25
Base de datos
¿Por qué la tabla auditoria_notas es inmutable? ¿Cómo lo garantizas?
voltear →
Respuesta
La inmutabilidad está garantizada a nivel de base de datos, no de política de código. Solo el trigger PL/pgSQL puede insertar en auditoria_notas. En la aplicación no existe ningún endpoint DELETE ni PUT sobre esta tabla, y ningún repositorio expone métodos de escritura directa sobre ella.
Tests y calidad
26
Tests
¿Qué es TDD y cómo lo aplicaste?
voltear →
Respuesta
Test-Driven Development: primero se escribe el test que describe el comportamiento esperado (Red), luego el código mínimo que lo hace pasar (Green), y finalmente se refactoriza sin romper nada (Refactor). En el proyecto, cada nuevo servicio o controlador tiene su test escrito antes o en paralelo a la implementación. El pipeline bloquea si la cobertura baja del 80%.
27
Tests
¿Cuál es tu cobertura de tests y cómo la mides?
voltear →
Respuesta
Cobertura de instrucciones medida con JaCoCo 0.8.12 integrado en el plugin Maven. El pipeline de GitHub Actions aplica un quality gate bloqueante: si la cobertura no supera el 80%, el job de tests falla y la promoción a pre-prod se cancela. El reporte se sube como artifact en cada ejecución.
28
Tests
¿Qué es Testcontainers y por qué lo usas para los tests de integración?
voltear →
Respuesta
Testcontainers levanta un contenedor Docker de PostgreSQL 16-alpine efímero por cada ejecución de tests. Garantiza paridad total con el entorno de producción: el mismo motor, los mismos triggers PL/pgSQL, el mismo comportamiento de transacciones. Alternativa descartada: base de datos H2 en memoria (no soporta PL/pgSQL ni JSONB).
29
Tests
¿Cuántos tests de seguridad tienes y qué cubren?
voltear →
Respuesta
32 tests en 6 clases: SecurityConfigTest (13 tests: acceso por rol, CSP, CSRF, snap-admin), CustomLoginSuccessHandlerTest (3: redirección por rol y mustChangePassword), LoginRateLimitFilterTest (3: HTTP 429, IPs independientes), SecurityAuditLoggerTest (6: log-injection, nulls), AuthIntegrationTest (6: login real con BD, sesiones concurrentes), LoginControllerTest (1).
30
Tests
¿Cómo evitas que los tests de integración se contaminen entre sí?
voltear →
Respuesta
Los tests de integración con @SpringBootTest usan @Transactional para envolver cada test en una transacción que se hace rollback al terminar. Testcontainers levanta un contenedor PostgreSQL fresco por ejecución. Para tests que necesitan comprobar el estado persistido (sin rollback), se limpian las tablas en el @BeforeEach.
CI/CD y despliegue
31
CI/CD
¿Cuáles son los cuatro jobs de tu pipeline y qué hace cada uno?
voltear →
Respuesta
1. Lint & Validation: Spotless (formato Java), hadolint (Dockerfile), actionlint. 2. Build Test Container: construye la imagen Docker en la etapa test con caché de GitHub Actions. 3. Containerized Tests: levanta PostgreSQL 16-alpine, ejecuta los 499 tests, verifica cobertura >80% con JaCoCo. 4. Purge & Promote: elimina herramientas dev, force-push a pre-prod, abre PR a main.
32
CI/CD
¿Qué es la política de purga y por qué existe?
voltear →
Respuesta
La rama dev contiene herramientas de IA, documentación técnica interna y el directorio conductor/. Antes de llegar a main (producción), el job Purge & Promote elimina automáticamente esos directorios (.agents/, .claude/, conductor/, GEMINI.md…) y hace force-push a pre-prod. Así el código productivo nunca expone metadatos de desarrollo.
33
CI/CD
¿Por qué usas un Dockerfile multi-etapa?
voltear →
Respuesta
El Dockerfile multi-etapa tiene una etapa build/test con JDK completo y Maven para compilar y ejecutar tests, y una etapa runtime con solo el JRE. La imagen final no incluye el código fuente, las herramientas de build ni el entorno de test. Resultado: imagen más pequeña, menor superficie de ataque y menor tiempo de deploy.
Implementación específica
34
Implementación
¿Cómo funciona la importación masiva de alumnos desde Excel?
voltear →
Respuesta
Tres fases atómicas: (1) Parsing: UsuarioExcelParserService lee el .xlsx con Apache POI. (2) Validación: UsuarioImportValidatorService verifica formato de email, política de contraseña, límite de 200 filas y duplicados en el lote. Si hay cualquier error, se lanza excepción y no se persiste nada. (3) Persistencia: upsert por username — si existe, reutiliza; si no, crea con mustChangePassword=true.
35
Implementación
¿Qué hace EvaluacionBootstrapService y cuándo se llama?
voltear →
Respuesta
Crea automáticamente la estructura mínima de evaluación para una impartición: un PeriodoEvaluacion ("Evaluación", peso 100) y un ItemEvaluable de tipo EXAMEN por cada RA del módulo. Es idempotente: comprueba existsByImparticionId antes de crear nada. Se llama desde AdminAlumnoService.asignarGrupo() por cada matrícula nueva. El import Excel NO lo llama.
36
Implementación
¿Cómo funciona la redirección post-login según el rol del usuario?
voltear →
Respuesta
CustomLoginSuccessHandler aplica esta lógica: (1) si mustChangePassword == true → /change-password. (2) Si tiene más de un rol funcional → /seleccionar-rol. (3) Si tiene un único rol → al dashboard de ese rol (/admin/dashboard, /centro-admin/dashboard, etc.). (4) Si no tiene ningún rol válido → /login?norole.
37
Implementación
¿Cómo funciona el portal del tutor? ¿Es un rol RBAC separado?
voltear →
Respuesta
No es un rol RBAC independiente. El tutor accede con ROLE_PROFESOR. Si el campo tutor_id de la tabla grupos apunta al usuario autenticado, el sistema habilita el portal /tutor/**. Si además el tutor es el profesor de una impartición concreta (puedeEditar=true), el enlace redirige al cuaderno del profesor; si no, muestra la vista de solo lectura.
38
Implementación
¿Cómo se asigna un alumno a un grupo y qué pasa después?
voltear →
Respuesta
AdminAlumnoService.asignarGrupo() itera todas las imparticiones del grupo. Por cada una que el alumno no tenga matrícula, crea una Matricula (ACTIVA) y llama a EvaluacionBootstrapService.bootstrapParaImparticion() para inicializar el PeriodoEvaluacion e ItemsEvaluables. Las imparticiones ya matriculadas se saltan silenciosamente. El método devuelve el número de matrículas creadas.
39
Implementación
¿Cómo funciona la exportación de auditoría a Excel?
voltear →
Respuesta
AuditoriaExcelExportService genera en memoria un XSSFWorkbook de Apache POI 5.3.0 con los registros de auditoria_notas. Se devuelve como flujo de descarga directa con Content-Disposition: attachment sin escritura en disco. El ADMIN_CENTRO solo exporta registros de sus centros asignados; el ADMIN exporta todo.
40
Implementación
¿Qué es un ResultadoAprendizaje y cómo se relaciona con la evaluación?
voltear →
Respuesta
Un ResultadoAprendizaje (RA) es un objetivo pedagógico del módulo, obligatorio por el Real Decreto 659/2023 de la LOFP. Cada RA se desglosa en CriteriosEvaluacion (CE) con pesos porcentuales. El profesor califica por CE, el sistema agrega CE→RA→Periodo→Global usando los pesos almacenados en BD. Los RA tienen también pesoSugerido para ponderar entre ellos.
41
Implementación
¿Por qué Bucket4j y no Nginx o un API Gateway para el rate limiting?
voltear →
Respuesta
Para el alcance del proyecto, Bucket4j in-process no requiere infraestructura adicional: ni Nginx, ni Redis, ni API Gateway. El cubo de tokens vive en memoria de la JVM. La contrapartida es que el estado no se comparte entre múltiples instancias de la app, pero con un despliegue monolítico en Docker esto no es un problema real.
42
Implementación
¿Cómo evitas que el Admin de Centro modifique usuarios con rol ADMIN?
voltear →
Respuesta
CentroAdminContextService.validateUsuarioGestionablePorCentroAdmin() inspecciona los roles del usuario objetivo antes de cualquier operación de escritura. Si detecta ROLE_ADMIN o ROLE_ADMIN_CENTRO, lanza AccessDeniedException, que Spring Security traduce en HTTP 403. La comprobación ocurre en la capa de servicio, no solo en la interfaz.

¿Qué es el tour de onboarding y cómo detecta el primer acceso?
voltear →
Respuesta
El tour está implementado con Driver.js y cargado desde CDN jsDelivr (CSP actualizada para permitirlo). El script admin-tour.js comprueba en localStorage la clave schooledule_tour_admin_visto. 44
Implementación
¿Por qué las credenciales del seed de desarrollo tienen contraseña "1234" si tienes política de contraseñas?
voltear →
Respuesta
La política @ValidPassword se aplica en los formularios de creación de usuario, no en las migraciones SQL. El seed V2__seeds_desarrollo.sql inserta directamente el hash BCrypt de "1234" en la BD sin pasar por el validador de la aplicación. Esto es intencionado: el seed es solo para entornos de desarrollo. Además, todos los usuarios del seed tienen must_change_password=true, así que el primer login fuerza a cambiar la contraseña a una que sí cumpla la política.
Producto y decisiones
45
Producto
¿Por qué no usaste Moodle como base en lugar de crear algo desde cero?
voltear →
Respuesta
Moodle tiene tres carencias estructurales: (1) no tiene el concepto de "sede" como unidad de aislamiento de datos, gestionar varias requiere instancias separadas. (2) Su auditoría de calificaciones puede ser alterada por el profesor. (3) No modela la jerarquía RA→CE obligatoria en FP por el Real Decreto 659/2023. Adaptar Moodle habría requerido reescribir su modelo de datos central.
46
Producto
¿Qué harías diferente si pudieras empezar de nuevo?
voltear →
Respuesta
Diseñaría el esquema de evaluación (Periodos, Items, Calificaciones) desde el primer commit con el modelo final, en lugar de migrarlo incrementalmente. El número de migraciones Flyway acumuladas refleja ese aprendizaje progresivo. También añadiría SonarQube al pipeline desde el inicio para detectar deuda técnica antes de que se acumule.
47
Producto
¿A qué normativa educativa se alinea el modelo de RAs y CEs?
voltear →
Respuesta
A la Ley Orgánica 3/2022 (LOFP) de Ordenación e Integración de la Formación Profesional y al Real Decreto 659/2023, que establece la evaluación por competencias mediante Resultados de Aprendizaje ponderados con Criterios de Evaluación. El modelo de Schooledule refleja directamente esa estructura jerárquica obligatoria para los ciclos FP.
48
Producto
¿Cómo escalaría el sistema si pasara de 200 a 20.000 alumnos?
voltear →
Respuesta
La arquitectura actual soporta escalado horizontal: múltiples instancias de la app detrás de un load balancer (las sesiones ya están en PostgreSQL, no en memoria local). Para el rate limiting habría que migrar Bucket4j a un backend compartido (Redis). El modelo de datos multi-sede ya está diseñado para múltiples tenants. PostgreSQL escalaría con réplicas de lectura para las consultas de auditoría.
49
Producto
¿Cómo gestionas el cambio de curso académico sin perder datos históricos?
voltear →
Respuesta
La entidad CursoAcademico actúa como eje temporal. Solo uno puede estar activo en cada momento; el admin lo marca con POST /admin/cursos/{id}/activar, que desmarca el anterior. Los datos de cursos pasados se conservan íntegramente y son accesibles mediante los filtros de la interfaz. El curso activo actúa como filtro por defecto en todas las listas del panel.
50
Producto
¿Cuál es la parte técnica de la que estás más orgulloso y por qué?
voltear →
Respuesta
La auditoría forense inmutable. No es un log de aplicación que se puede desactivar o borrar: es un trigger PL/pgSQL que actúa directamente en la base de datos, fuera del alcance del código Java. Transmitir el email del profesor a través de set_config de PostgreSQL dentro de la misma transacción JPA fue el reto técnico más interesante del proyecto, y el resultado resuelve un problema legal real.
