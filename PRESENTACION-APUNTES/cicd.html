Infraestructura — GitHub Actions

Pipeline CI/CD

Estrategia de ramas, jobs de automatización, calidad de código y flujo Purge & Promote.

Estrategia de ramas

dev desarrollo activo → CI pasa → pre-prod purge automático → PR manual → main producción
Rama Propósito Contenido
dev Desarrollo activo Todo el código + conductor/ + GEMINI.md + herramientas IA
pre-prod Rama limpia auto-generada Solo código fuente (archivos de dev purgados)
main Producción Solo código de producción. PR manual desde pre-prod

Workflows de GitHub Actions

ci-cd.yml

Workflow principal. Se dispara en push a dev o feature/**, y en PR a dev.

memoria-pdf.yml

Compila el PDF de la memoria LaTeX. Se dispara cuando hay cambios en memoria/. Artifact de 30 días.

Jobs del pipeline principal (ci-cd.yml)

Job Timeout Depende de Descripción
1. lint-validation 5 min — Pre-commit hooks + actionlint + hadolint
2. build-docker-test 10 min lint Build imagen Docker target=test, guarda como artifact
3. containerized-tests 15 min build Carga imagen, lanza tests con Postgres real, verifica JaCoCo ≥80%
4. purge-promote 10 min test (solo push a dev) Crea rama pre-prod limpia, force push, crea PR → main

Job 1 — Lint & Validation

  • Checkout código + JDK 21 (Temurin) + Python 3.12
  • Ejecuta pre-commit hooks (excepto spotless-apply y maven-check)
  • Valida workflows con actionlint
  • Lintea el Dockerfile con hadolint (ignora DL3018)

Job 3 — Tests en contenedor

  • Servicio PostgreSQL 16-alpine en CI con healthcheck
  • Credenciales de test: user=admin, password=password123, db=schooledule
  • Ejecuta mvn verify -DskipTests=false -B dentro del contenedor
  • JaCoCo verifica cobertura ≥ 80% → falla el job si no se cumple
  • Sube informes de tests en caso de fallo (retención 5 días)

Purge & Promote (Job 4)

Solo se ejecuta en push a dev (no en PRs). Crea la rama pre-prod limpia eliminando todos los archivos de desarrollo:

Archivos eliminados

  • .agents/
  • conductor/
  • .gemini/
  • .idea/
  • target/
  • GEMINI.md
  • CLAUDE.md
  • plan.md
  • skills-lock.json

Lo que queda en pre-prod

  • Código fuente (src/)
  • Configuración Maven (pom.xml)
  • Infraestructura (infraestructura/)
  • Migraciones Flyway
  • GitHub Actions workflows
  • Pre-commit config
Tag de build: Cada promote crea el tag build-{RUN_NUMBER}-{SHA} y abre (o actualiza) automáticamente el PR de pre-prod → main.

Pre-commit hooks

Ejecutados localmente antes de cada commit y en el job de lint del CI:

Hook Qué hace
trim trailing whitespace Elimina espacios al final de línea
fix end of files Asegura newline final en cada fichero
check yaml Valida sintaxis de ficheros .yml
check xml Valida sintaxis de ficheros .xml
check for added large files Bloquea ficheros > 2.5 MB (configurable)
check json Valida sintaxis de ficheros .json
check for merge conflicts Detecta marcadores de conflicto sin resolver
Detect hardcoded secrets Busca credenciales hardcodeadas en el código
Spotless Apply Formatea Java automáticamente (Google Java Format)
Prettier Formatea HTML, CSS, JS, JSON
Maven Validate Valida que el pom.xml es correcto

Preguntas frecuentes

¿Qué es Purge & Promote?

Es el flujo automático que, tras pasar los tests en dev, crea una rama pre-prod eliminando todos los archivos de desarrollo (documentación técnica, herramientas IA, etc.). Garantiza que solo llegue código de producción a main.

¿Qué herramienta mide la cobertura de tests?

JaCoCo. Está configurado con un umbral del 80%. Si la cobertura cae por debajo, el job de tests falla y no se promueve el código.

¿Los tests usan una base de datos real?

Sí. En el job 3 del pipeline se levanta un servicio PostgreSQL 16-alpine con Docker. Los tests de integración se ejecutan contra esa base de datos real, no contra H2.

¿Qué hace hadolint?

Es un linter para Dockerfiles. Verifica buenas prácticas (por ejemplo, versiones fijadas en FROM, uso de --no-cache en apk, etc.). En el pipeline ignora la regla DL3018.
